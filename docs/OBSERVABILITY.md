# 操作日志与执行监控要求（待实现）

更新：2026-11-11。老师提出的“按钮→API→后台步骤→结果”追踪要求已确认；本页是后续开发和验收契约，不代表本轮已实现统一监控。

## 现有能力

Legacy已有backend/services/observability.py的生命周期、失败、状态及GPU记录；Room8任务已有status、逐帧manifest、Blender/编码日志、timing_report和GPU证据。它们没有完整覆盖所有API、CLI、前端动作，也没有统一贯穿各层的trace_id。后续扩展复用现有数据，不另建一套相互冲突的渲染状态机。

## 必须记录的边界

每次API请求、用户操作、CLI运行和后台任务的关键阶段应可关联追踪，包括参数校验失败、异常和中断。前端点击不是只打印console：后续需要明确的事件上报与后端接收方案；前端尚未开发，不能宣称浏览器事件已持久化。不要求每个内部函数或循环都逐条记录。

```text
点击“开始渲染” → 发起请求 → 后端接收 → 校验房间/资产/配置
→ 冲突检查 → 创建job → 启动Blender → 渲染 → 编码 → 解码检查
→ 发布产物 → 前端显示完成/播放；失败则保留失败阶段及证据
```

| 字段 | 约定 |
| --- | --- |
| ts | UTC ISO时间，界面可转换为Asia/Shanghai |
| trace_id | 一次用户操作/CLI到任务的关联ID；缺失时由后端生成并返回，外来值需校验 |
| request_id | 每次HTTP请求的ID；轮询请求有独立ID，可继续关联同一job |
| span_id / parent_span_id | 串联验证、读取、启动、编码等阶段 |
| operation / stage / event | 动作、阶段及start/success/failure/cancel等结果 |
| method / route / status_code | API方法、路由模板和HTTP结果，避免带秘密的完整URL |
| scene_code / room_id / asset_version / job_id / attempt_id | 已核验业务上下文，缺少则留空，不伪造数据库ID |
| duration_ms | 使用本进程单调时钟；开始事件可为空，结束事件记录耗时 |
| error_code / error_type | 失败分类，详细堆栈进入受控日志 |
| actor | 有真实认证时记录主体ID；没有认证不伪造用户身份 |

HTTP请求耗时、后台任务总耗时和阶段耗时分别记录。接口快速返回“已创建”不等于渲染完成；不能跨机器直接相减浏览器/服务器时间当作精确耗时。保留失败和缺失事件，不用成功记录覆盖历史错误。

## 实现顺序与存储

下一任务先实现后端请求中间件、公共阶段计时/错误记录和CLI上下文，再接现有Room8任务；网页开发时接按钮、请求、结果及播放动作。第一版使用标准结构化日志和JSONL，不先引入额外监控集群。

计划的服务日志和任务事件流应区分：服务请求按日期保存，任务事件归对应render_jobs目录；现有逐帧/GPU文件继续复用。准确目录、轮转、并发追加和保留周期在实现时明确并测试，当前不把拟议文件名写成已有产物。可读HTML/Markdown时间线由结构化事件生成，不为每次点击人工维护文档。

监控先展示请求数量/失败率/耗时、任务阶段/进度/失败位置及已有GPU采样；区分“缺数据”和“零值”。日志不是鉴权、数据库审计或全局调度器的替代品。

## 数据保护与验收

- 不记录密码、DK_APPKEY、Authorization、完整签名URL、原始全景/户型响应、任意请求体或无界文本；字段使用允许列表并限制长度。
- 新功能测试覆盖成功、失败、校验拒绝、关联ID传递和耗时；后台任务返回后仍能关联至同一trace/job。
- 日志组件故障策略需明确：不能因普通日志写入失败无说明地丢失业务结果，也不能吞掉实际任务失败。
- 高频轮询保留可核对的请求结果，聚合展示与原始记录分开；不复制逐帧大文件到请求日志。
- 堆栈和内部路径只向授权维护者提供。前端上报视为不可信数据，防止日志注入和泄露。
- 实现后选一次CLI和一次API展示时间线；网页落地后再验收真实按钮闭环，不用模拟事件冒充前端已完成。
